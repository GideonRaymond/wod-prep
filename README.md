# WOD Prep

Paste a CrossFit workout and get it broken down by movement — with videos, points of performance, articles and (soon) alternative movements for each.

## Setup

```bash
npm install
cp .env.example .env.local   # then add your ANTHROPIC_API_KEY (and YOUTUBE_API_KEY for videos)
npm run dev
```

Open http://localhost:3000.

## Parsing, in two steps

**Break it down** streams its progress, so the review page fills in while the workout is read:

1. **The structure** comes back in a few seconds from a quick read by Claude Haiku (`FAST_MODEL`): each part's label, title, kind (warm-up, part, cool-down) and lines. A warm-up or cool-down gets a label that says so.
2. **Each part's details** are then read at the same time, one Claude call per part: format, movements, stimulus, minutes and equipment.

`POST /api/parse` answers with newline-delimited JSON (`ParseEvent` in `src/types/parse.ts`): an `outline` event, a `part` event as each part finishes, then `done` with the whole workout, or an `error`. A cached workout streams the same events at once. While parsing, the home page shows a checklist ("Reading your workout", then each part found, ticked off as it's read).

## Loading screen

After **Confirm workout**, the workout page shows a loading screen while the class is still being built (reading, videos, the warm-up and skills plan). This follows the WOD Prep design system's **LoadingScreen**.

- **Left:** the pasted workout on a whiteboard. Each block's first line is in Permanent Marker and the rest in Kalam, in purple inks only; both fonts are loaded with `next/font/google` and used only here. Each part gets circled in turn, with its marker. On phones the board is capped with a fade and a **Show all** button.
- **Right:** a checklist (`classChecklist`) with these rows:
  - **Reading your workout**, **Before class**, **Warm-up**, **Workout** and **Cool-down**.
  - The Workout row grows into this workout's own parts and skills, in class order. A part ticks off once its videos are found, and skills appear once the plan arrives.
  - **Timing the class** comes last, with every stage's start minute.
- **Maybe while you wait:** the Before class reading shows as soon as it's found.
- **Opening the class:** "Your class is ready" appears with **Open your class** and a 3-second countdown. The countdown pauses while the pointer or focus is on the reading list. Then the screen fades out, the class page's stages settle in 60 ms apart, and focus moves to the page heading.
- **Accessibility:** a polite live region announces each step ("Warm-up ready") and when the class is ready. With `prefers-reduced-motion`, nothing slides or fades.
- **When it's skipped:** if everything is already there when the page opens (say, after a refresh), the class shows straight away.

## Parse cache

In development, every parsed WOD is saved to `.cache/parsed-wods.json` and every AI-generated set of points of performance to `.cache/points-of-performance.json` (both gitignored), so testing with the same workouts costs nothing after the first time. Cached results even work without an API key.

- **Formatting is ignored:** `"Fran" 21-15-9 for time: Thrusters (95/65 lb), Pull-ups` and `fran 21-15-9 for time thrusters 95/65lb pullups` hit the same entry.
- **Multi-part WODs** are also cached part by part, so pasting just one part of a day you parsed before (e.g. only its Part B) is a hit.
- **Named workouts** (and named parts) are also stored under their name, so after parsing Fran once, even as Part B of a longer class, typing just `Fran` is a cache hit. Made-up titles like "Intense Couplet" aren't.
- **Different wording** (e.g. `21-15-9 pullups and thrusters`) is parsed once more, then cached too.
- Responses carry an `X-Cache: HIT` or `MISS` header (visible in the browser's network tab).
- **Clear the cache:** delete `.cache/`. **Turn it on or off:** set `WOD_CACHE=on|off`. It's off in production by default.
- Bump `CACHE_VERSION` in `src/server/wodCache.ts` (or `POINTS_CACHE_VERSION` in `src/server/pointsOfPerformance.ts`) when that prompt or schema changes.

## Points of performance

On the workout page (after **Confirm workout**), each movement card has a collapsible **Points of performance** section (cues plus common faults), loaded the first time it's opened.

- About 25 common movements have hand-written points in `src/data/pointsOfPerformance.ts`. They're free and instant, and need no API key. Add a movement or an alternative name there to cover more.
- Other movements are generated by Claude, cached, and marked "Generated by AI".

## Videos

When the workout page opens, it finds videos for each movement (and for each named workout, like Fran or Murph) and lists a short pick under **Watch** in each part's **Before class** panel:

- **One video per movement** — two when the part is a single movement, like a run.
- **One extra video about the workout itself** when it's a named workout.
- **No repeats:** if a movement's best video is already shown, its next one is used.

The videos are stored with the workout, so a refresh doesn't search again.

Where they come from:

1. **Hand-picked:** the ~30 standard movements (the ones with curated points of performance) have one video each in `src/data/movementVideos.ts`, mostly the official CrossFit channel's short demos. Free, instant, no key needed. Swap a video by editing its entry; a test checks every curated movement has one.
2. **Searched and picked by Claude:** everything else (and named workouts) is searched on YouTube (15 results), then Claude picks up to three, best first, with a one-line reason shown under the link. It prefers technique demos from credible coaches for movements, and strategy, pacing and scaling for named workouts, and skips vlogs, challenges and competition footage. Claude can only pick from YouTube's results, so every link is real.

- Search uses the [YouTube Data API](https://developers.google.com/youtube/v3/getting-started): create a key in Google Cloud (enable "YouTube Data API v3", then Credentials → Create API key) and set `YOUTUBE_API_KEY`. The free quota is about 100 searches a day.
- **Fallback ranking** (no `ANTHROPIC_API_KEY`, or Claude fails): the official CrossFit channel first, then titles that name the movement, then YouTube's order. Livestreams and videos over 20 minutes are always skipped. Three per search are kept, as spares for avoiding repeats.
- Results are cached per movement in `.cache/movement-videos.json` for **30 days**, then searched again. Any spelling of a movement shares one entry ("Pull-ups" = "pull up"). Bump `VIDEOS_CACHE_VERSION` in `src/server/movementVideos.ts` when the search or ranking prompt changes.

## Articles

The workout page also finds up to three articles for each part (parts without movements are skipped) and lists them under **Read** in **Before class**, each with a one-line reason. Claude searches the web itself (`web_search` + `web_fetch`) and aims for a mix of angles, at most one each:

- **Mechanics:** why we do a movement, or the mechanics at work. Not generic "how to" lists.
- **Energy:** the energy system, pacing, recovery or fuel the workout depends on (VO2 max for a 2k row, zone 2, fueling a long grind).
- **Tie-in:** something surprising but genuinely connected, like the workout's history.

Where it looks:

- **CrossFit's own writing first:** crossfit.com and the CrossFit Journal. Many Journal articles are free as PDFs at `library.crossfit.com/free/pdf/`, which Claude can read.
- **journal.crossfit.com needs a login,** so Claude can't open those pages. It may still pick one from its search title and description, and the link shows **Login needed**. Unofficial copies of Journal articles are never used.
- **Then established coaching and sports-science sources.**

Only links that came back from Claude's own searches are kept, so a made-up URL never shows. Results are stored with the workout and cached in `.cache/articles.json` for **30 days**: named workouts by name, other parts by format, scheme and movements. A search takes about 30–40 seconds per part. Bump `ARTICLES_CACHE_VERSION` in `src/server/articles.ts` when the prompt changes.

## Warm-up and skills

The workout page plans the start of class with one Claude call per workout, sized to a **60-minute class for about 12 athletes**:

- **Time budget:** 60 minutes, minus the 5-minute whiteboard, minus every part's minutes (programmed warm-up and cool-down included), minus 5 minutes to wrap up when no cool-down is programmed. Claude is told how much is left.
- **Warm-up** (skipped when the workout already has a programmed warm-up), in this order:
  1. About 2 minutes of easy cardio, if time allows.
  2. Dynamic stretching, which has priority over the cardio.
  3. Today's movements, building toward working loads.
- **Skills,** only for skill movements (gymnastics like rope climbs, T2B, muscle-ups, HSPU, double-unders, kipping pull-ups; technical lifts like the snatch, clean and jerk or OHS):
  - Progressions run from the simplest step to the full movement, each with its time, dose, coaching point and when to move on.
  - At most two skills. Each comes **right before the first part that uses it**, so practice for OHS in B sits between A and B.
- **Realistic timing:**
  - The prompt counts explaining and demoing each step, practicing with feedback for 12 people, rotating on shared equipment (3–4 ropes, 4–6 rowers) and 2–3 minutes of setup.
  - Then `fitPrep` (`src/utils/classPlan.ts`) checks the plan against the budget: it drops the hardest progressions or whole skills that don't fit, never the warm-up.
- The plan's start times show on each stage. Its equipment is added to **Equipment today**.
- **Saving:** the plan is stored with the workout and remembers what it was planned for, so editing the workout plans again.
- **Caching:** plans are cached in `.cache/class-prep.json` for 30 days. Bump `PREP_CACHE_VERSION` in `src/server/classPrep.ts` when the prompt changes.

## Cool-down stretches

Every class ends with **suggested stretches, if time allows**. No time is set aside for them. They're added under a programmed cool-down, or get a **Cool-down** stage of their own at the end.

- **Library:** about 40 stretches in `src/data/stretches.ts`. Each has the body areas it targets, a dose, any equipment (band, box) and a short hand-picked YouTube demo shown as a **Watch** link. Swap a video by editing its entry.
- **Which areas:** movement names are mapped to the areas they work (`MOVEMENT_AREAS`, e.g. thrusters → quads, glutes, shoulders, hip flexors), falling back on the movement's category.
- **Which stretches** (`suggestStretches`): up to 3 (`STRETCHES_PER_CLASS`), one per area, starting with the areas the workout works most. Areas an earlier pick already covers are skipped.
- **Variation:** the pick is random but seeded by the workout's text, so a workout keeps its stretches across refreshes, while next week's squat day gets different ones (not always the couch stretch). Stretches aimed at that area, and stretches covering more of what the workout works, are favored.
- A test checks every area has at least 3 stretches to choose from (2 for triceps and forearms).

## Structure

```
src/
├── app/                  # Next.js routes only (pages, layouts, API route handlers)
│   ├── page.tsx          #   renders <HomePage />
│   └── api/              #   POST /api/parse (streamed), /api/points-of-performance, /api/videos, /api/articles, /api/class-prep
├── components/
│   ├── shared/           # Reusable UI (Button, ButtonLink, TextArea, Card, Badge, Dialog, IntensityGauge, MovementDetails, …)
│   ├── home/             # Review page: paste, check and edit the parsed workout (HomePage, WorkoutPart, …)
│   └── workout/          # Workout page: details after confirming (WorkoutPage, PointsOfPerformance, …)
├── hooks/                # React hooks (useParseWod, useUndoableText, useAutoResize, …)
├── providers/            # App-wide state (WodProvider: the current workout, shared by both pages)
├── stores/               # External stores (wodStore: keeps the workout and its text in sessionStorage across refreshes)
├── services/             # Client-side API calls (wodApi)
├── server/               # Server-only code (the Claude call); never imported by components
├── schemas/              # Zod schemas and the types inferred from them
├── types/                # Hand-written shared types (UI state)
├── constants/            # App-wide constants (limits, labels, example WOD)
├── data/                 # Hand-written content (curated points of performance)
├── styles/               # Shared Tailwind class helpers
├── utils/                # Small pure helpers (cn, withId)
└── test/                 # Test setup and fixtures
```

Each component has its own folder with the component, its tests and an `index.ts`:

```
components/shared/Button/
├── Button.tsx
├── Button.test.tsx
└── index.ts              # import { Button } from "@/components/shared/Button"
```

Middleware is called **proxy** in Next.js 16 and must live in a single `src/proxy.ts`. There isn't one yet.
